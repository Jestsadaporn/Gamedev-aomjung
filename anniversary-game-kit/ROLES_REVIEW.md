# ทบทวนบทบาทและแบ่งเจ้าของงาน

สามบทบาทเดิมในบทสนทนาคือ **Game Designer, Game Developer และ Game QA Tester** คำว่า “นักพัฒนาเกม” ในที่นี้ต้องแยกจาก Designer ให้ชัด เพื่อไม่ให้เกิดเจ้าของงานสองคนในเรื่องเดียวกัน

## ปัญหาของขอบเขตเดิมและสิ่งที่ปรับ

| บทบาท | จุดขาดหรือกว้างเกินไป | ปรับหน้าที่ให้ชัด |
|---|---|---|
| Designer | ต้องคิด 3 คอนเซปต์พร้อมโลก เนื้อเรื่อง ระบบ ภาพ เสียง Engine และแผนพัฒนา ทำให้ช้า; ขาดค่ากติกาและสถานะที่ Dev นำไปทำได้ | ออกแบบคอนเซปต์เดียวสำหรับ MVP กำหนดกติกา/สถานะ/เส้นทาง 15 นาที, UX มือถือ, บทและ Asset specification; ให้ Dev เลือกวิธีเขียนและ Engine ให้ Producer ดูแลขอบเขต |
| Developer | รับทั้งการตัดฟีเจอร์ เลือกประสบการณ์ ประเมินความสนุก ทดสอบทุกอุปกรณ์ และตัดสินความพร้อมส่ง | รับผิดชอบโค้ด รวม Asset ทดสอบระดับพัฒนา และ Build/Deploy/Rollback; เสนอ trade-off ได้ แต่ Producer/กันตัดสินขอบเขตและ QA ตรวจแยก |
| Tester | รายการตรวจยาวแต่เกณฑ์บางส่วนยังไม่มี อาจกลายเป็นคนกำหนดเกมหรือรับประกันทุกมือถือ | เริ่มจากทดสอบตามความเสี่ยง ใช้ Acceptance Criteria ที่ตกลง ระบุ Build/อุปกรณ์/หลักฐาน แยกบั๊กจากความเห็น และตรวจซ้ำ ไม่ออกแบบใหม่หรือแก้โค้ดโดยอัตโนมัติ |
| Product Owner / Producer (เพิ่ม) | เดิมไม่มีเจ้าของ Backlog การตรึงฟีเจอร์ การติดตาม blocker และการรับความเสี่ยงก่อนส่ง | ดูแลลำดับงาน ขอบเขต กำหนดส่ง dependency และบันทึกการตัดสินใจ ประสานข้อมูลจากกัน เสนอความพร้อมส่ง กันเป็นผู้รับงานและตัดสินใจสุดท้าย |

## งานที่เคยขาดและเจ้าของใหม่

- **เกณฑ์รับงานที่ตรวจได้:** Designer ร่างรายฟีเจอร์, Dev เช็กความเป็นไปได้, QA เช็กว่าทดสอบได้, Producer เก็บเวอร์ชันที่ตกลง
- **ภาพ/เสียงและสิทธิ์ใช้งาน:** Designer ทำรายการขนาด/เฟรม/ทิศ/Anchor/ชื่อไฟล์/ที่มา/สิทธิ์/สถานะ; Dev รวมและตรวจไฟล์; กันให้/ยืนยันความทรงจำส่วนตัว การกำหนด Art Direction ไม่ใช่หลักฐานว่า Asset วาดเสร็จแล้ว
- **UX บนมือถือและการเข้าถึงพื้นฐาน:** Designer ระบุปุ่ม ขนาดตัวอักษร ช่องว่างปลอดภัย และการสื่อสาร; Dev ทำ; QA ตรวจอุปกรณ์จริงและการใช้หลายสัมผัส
- **ความต่อเนื่องของสถานะ:** Designer กำหนดกติกา Dialogue/Pause/Defeat/Outfit/Scene; Dev ทำ state transition; QA ทดสอบข้ามระบบ
- **Release และ rollback:** Dev จัดแพ็กและวิธีย้อนรุ่น; QA ตรวจรุ่นผู้สมัครบน URL จริง; Producer เก็บ Known issues และเสนอส่ง; กันตัดสินส่ง
- **เวลาเล่นและความรู้สึก:** Designer ตั้งสมมติฐาน, QA/ผู้เล่นใหม่วัดเวลาและสังเกต, Dev ปรับตามข้อกำหนดที่ตกลง ห้ามใช้ความเห็นของ AI แทนหลักฐานว่าคนเล่นสนุก

## ตารางเจ้าของผลลัพธ์

| ผลลัพธ์ | เจ้าของหลัก | ผู้ช่วย/ผู้ตรวจ | ผู้ตัดสินใจ |
|---|---|---|---|
| Backlog/ขอบเขต/กำหนด/เปลี่ยนแผน | Producer | Designer, Dev, QA | กัน |
| Mini GDD/เนื้อเรื่อง/กติกา/UX | Designer | Dev ตรวจทำได้, QA ตรวจทดสอบได้ | กันผ่าน Producer |
| Asset specification/รายชื่อแหล่งที่มา | Designer | Dev ตรวจรูปแบบไฟล์, กันให้เนื้อหาส่วนตัว | กันยืนยันเนื้อหาส่วนตัว |
| โค้ด/รวม Asset/บันทึก/ประสิทธิภาพ | Dev | QA ทดสอบ, Designer ตรวจเจตนา | เกณฑ์ที่ตกลงไว้ |
| Test plan/bug report/retest/QA report | QA | Dev อธิบายระบบ, Designer ยืนยันกติกา | QA รับรองเฉพาะสิ่งที่ตรวจจริง |
| Build/Deploy/rollback ทางเทคนิค | Dev | QA ตรวจ URL, Producer ติดตาม | ตามสิทธิ์และคำสั่งที่กันให้ |
| Release readiness/ข้อจำกัดก่อนส่ง | Producer | QA ให้หลักฐาน, Dev ให้ Build | กัน |

ไม่เพิ่ม Artist, Sound Designer, DevOps หรือ Security เป็นบทบาทแยกในกำหนดสั้นนี้ หากใช้ Asset สำเร็จรูปที่มีสิทธิ์และระบบ Static งานเหล่านี้จัดอยู่กับ Designer/Dev ตามตาราง หากต้องผลิตภาพเคลื่อนไหวเฉพาะจำนวนมาก ควรเพิ่ม **Pixel Artist แบบมีขอบเขตงานจ้างชัดเจน** หรือให้ Producer ลดความซับซ้อน ไม่โยนงานทั้งหมดให้ Dev เงียบ ๆ

## กติกาส่งต่องาน

ทุกการส่งงานใช้แบบนี้:

```text
จากบทบาท / ถึงบทบาท:
Backlog ID:
เอกสารเวอร์ชัน หรือ commit/build:
ผลลัพธ์และตำแหน่งไฟล์:
เกณฑ์ที่ตรวจเองแล้ว + หลักฐาน:
สิ่งที่ยังไม่ทำ / blocker / known issues:
สิ่งที่ต้องการให้อีกบทบาททำต่อ:
การตัดสินใจที่ยังรอกัน:
```

สถานะงาน: Todo → Ready → In progress → Ready for QA → Done; ใช้ Blocked พร้อมเหตุผลได้ทุกช่วง Dev ส่ง Ready for QA ไม่ใช่ Done จน QA มีหลักฐานผ่าน Must และ Producer บันทึกรับงานตามเกณฑ์ เอกสาร/งานเนื้อหาให้ QA ตรวจเกณฑ์ที่เกี่ยวข้อง ไม่บังคับใช้ runtime test กับเอกสาร

Ready = เป้าหมาย/เกณฑ์รับงาน/ข้อสมมติ/สิ่งที่ต้องใช้ชัดพอเริ่มได้ Done = ทำตามเกณฑ์ครบ ตรวจในขอบเขตที่ระบุ และไม่มีข้อผิดพลาดสำคัญค้าง หากยังตรวจอุปกรณ์หลักไม่ได้ให้คง Blocked/Ready for QA พร้อมความเสี่ยง ห้ามนับผ่านแทน

เมื่อ QA พบปัญหาให้เชื่อม PB ID และ Build เดิม Dev ระบุ Build ที่แก้แล้ว QA ตรวจซ้ำกรณีนั้นและระบบที่เกี่ยวข้อง Producer อัปเดตสถานะโดยไม่ลบประวัติปัญหา
